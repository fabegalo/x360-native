# x360-native v1.28.28 — Stable Release

This stable release follows v1.28.17. It lets Windows installations live in deep folders with Unicode names, without changing any Windows setting, and uses less disk space. It also fixes the Guide's Sign In and a crash when opening the debug overlay with F3. It includes the work prepared for v1.28.18, which was not published.

## Fixed

- **Guide Sign In:** choosing a profile from the Guide failed on every installation. The original 17559 sign-in module asks for a memory class that the runtime refused, so sign-in stopped before it started. The runtime now accepts every virtual memory class, as the original console does. Physical memory classes are still refused explicitly. A new test covers this. Sign In on screen has not been exercised since the fix.
- **F3 closed the game:** opening the debug overlay with F3 corrupted memory. The 17559 dashboard and Castle Crashers then closed with `STATUS_HEAP_CORRUPTION`, on the first press or within a few. The game and the runtime disagreed on the overlay's size. They now agree, and the dashboard survived 40 F3 presses in a row with the overlay open. A new test covers this.
- **Deep installation folders:** the 141-byte limit of v1.28.18 for preparing titles is gone. When the installation's tool or SDK folder is too long for Git, CMake or Ninja, it becomes a junction to a short folder under `%LOCALAPPDATA%\x360n` before any tool starts. This needs no privilege, Windows setting or short (8.3) names. Games, dashboards, saves, profiles and title outputs stay in the installation.
- **Deep folders inside the runtime:** the code generator, the log file, the game root check and the dashboard's Guide host now open names beyond 260 characters. Before, a deep installation stopped with "File could not be opened for reading", a crash of the dashboard after one second, "--game_data_root does not exist", or Castle Crashers stopping with "Missing verified dashboard system UI host".
- **One filesystem layer (from v1.28.18):** every file operation of the launcher, extraction, import, catalog, SHA-256 verification, preparation, update and removal goes through one layer. Paths stay ordinary and become the Windows extended-length form (`\\?\` or `\\?\UNC\`) only for the actual I/O, up to about 32,000 characters. Every move and replacement uses one rename of that layer. Windows junctions are treated as links by the containment checks.
- **Processes from deep folders (from v1.28.18):** Windows cannot start a process in a folder beyond 258 characters. Such a process starts in the same folder reached through a short junction to its installation, `%LOCALAPPDATA%\x360n\r\<id>`. The junction is checked before every use.
- **Short, isolated title builds (from v1.28.18):** each title compiles in a short private folder under `%LOCALAPPDATA%\x360n\b`, and its executable and modules are copied next to its receipt in the installation.

## Less disk space

- **Imports:** importing a game package or disc image hard-links the verified files from the app's own temporary extraction instead of copying them again. A Castle Crashers package wrote 1.1 MB instead of 144.9 MB. Folders you import yourself are still copied, so your originals stay yours.
- **Tools:** the downloaded tool archives (about 961 MB) are removed once their extraction is verified against the pinned hash.
- **SDK builds:** the titles share one SDK build instead of one per title. Old SDK builds that can no longer be used are removed. Builds in use, current builds and builds of other owners are kept.

## Updating

The launcher checks GitHub Releases at startup and offers newer stable versions after asking you. It verifies the downloaded archive before installing it and keeps your data, imported games, saves and profiles. The runtime changed, so the dashboard and your games need preparation again; the first preparation after the update compiles them.

## Verification and limitations

End to end on Windows x64, on an NTFS volume without short (8.3) names, in a clean 337-character, 363-byte installation folder with accents, Chinese, Japanese and an emoji, the launcher:
- imported the 17559 dashboard and Castle Crashers;
- prepared both (a second preparation reused the shared SDK build, and reopening only verified);
- started the dashboard.

From My Games, Castle Crashers reached the Guide and character selection. Play beyond that was not confirmed in that folder.

The new and existing tests cover:
- paths up to 2048 characters, Unicode and real UNC shares;
- junctions, the short dependency folders, processes started from deep folders, preparation measured against this checkout, the SDK builds that are kept and removed, and hard-linked imports.

The symbolic-link case needs a privilege that the test account lacks, so it is reported as skipped, not as passed. Passing these does not prove that every original game behaves correctly in a deep folder; check your library by hand with this release.

Remaining limits:
- **Network shares and file systems without junctions:** they can import but cannot prepare titles. Preparation stops with the cause. On a share, Windows also refuses to move a file between folders once the share-relative name passes about 500 characters.
- **macOS:** a path cannot reach 1,024 bytes, a system limit.
- **`%LOCALAPPDATA%` length:** it must be short enough for the `t`, `e` and `b` folders.
- **Hard links:** they need the extraction and the library on the same volume; otherwise the import copies once.
- **Profile creation:** the crash of the 17559 dashboard right after creating a profile is still open.
- **Platforms:** Windows x64 is still the only platform with end-to-end evidence. No new game compatibility or GPU performance is claimed.
